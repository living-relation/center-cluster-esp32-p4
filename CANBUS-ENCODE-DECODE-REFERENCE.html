CAN encode / decode reference

Every channel the Link G4X XtremeX broadcasts to the center cluster, with the ENCODE side (what the ECU puts on the wire) and the DECODE side (what the cluster firmware computes) together — so ECU and cluster scale/offset never get confused. This HTML file is the single canonical CAN reference; a machine-readable copy of the map is embedded at the bottom.

ENCODE — ECU / PCLink transmit: wire = round(value × Mult ÷ Div) + Offset DECODE — cluster firmware (main/canbus.c)
⚠️ Never copy a DECODE value into PCLink. The ECU multiplier is the reciprocal of the cluster scale and the ECU offset is the negative of the cluster offset. Lambda is ×1000 on the ECU and ×0.001 in the cluster — same relationship, opposite direction.
Two systems, one table. Everything you configure is on the ECU, in Link PCLink G4X → CAN Setup — the green ENCODE columns, the Apply steps, and the Link CAN Lambda setup. The blue DECODE columns just describe what the cluster firmware (already flashed) does with each value, so you can confirm the ECU settings produce the right on-screen reading. Nothing here requires editing the cluster's repo/firmware.

Bus / topology

ECULink G4X XtremeX
Bus — everything is on ECU CAN11 Mbit/s · big-endian (MS byte first) · standard 11-bit IDs · 8-byte frames. The ECU's CAN2 is unused by this system.
Nodes on CAN1the XtremeX ECU, the center cluster (ESP32-P4, TWAI TX=GPIO5 / RX=GPIO4 via SN65HVD230), and the external Link CAN Lambda module — all share this one bus. Side displays follow over UART (not CAN).
Lambda sourceno onboard wideband — the external Link CAN Lambda module (on CAN1, same bus) feeds the Lambda 1 parameter, which the XtremeX rebroadcasts on 0x3EA. The ECU must be configured to receive from the module (see the Link CAN Lambda section below) before it can forward lambda.

Boost gauge: vacuum vs. boost display

The CAN config is identical for both options below — the ECU always sends MAP absolute (kPa) on 0x3E8 bytes 2–3. The cluster computes boost_psi = (MAP − 100) × 0.145038, which is already signed (negative below ~100 kPa = vacuum, positive above = boost) and stays signed all the way to the side display over UART. The only difference is the boost gauge's display range:

  • Negative vacuum + positive boost: set the boost gauge minimum negative (e.g. −15 to +30 psi). No CAN or firmware change — the value is already signed. Units: wire = MAP kPa absolute; display = PSI gauge (signed).
  • 0 in vacuum, positive boost (current, 0 → +30 psi): floor the gauge minimum at 0. Same CAN config and units; vacuum just reads 0.
Simpler route: keep MAP absolute (what's already configured) for both. To show vacuum, change only the boost gauge's minimum on the display side — nothing in the CAN config, units, or center firmware changes. Do not switch the ECU to send MGP (gauge pressure): that would require a firmware change to drop the −100 offset, for no benefit.
Engine-off / key-on reading, and altitude: the gauge subtracts a fixed 100 kPa (≈ sea-level ambient), so with the engine off the MAP sensor reads ambient barometric pressure and the value is (ambient − 100) × 0.145038. At elevation your ambient is below 100 kPa, so that value is slightly negative (≈ −1 psi around 2,000–2,500 ft). With the current 0→+30 gauge (floored at 0) it displays 0; a vacuum-capable gauge would show the small negative. To read exactly 0 engine-off regardless of altitude you'd have to reference barometric (BAP) instead of a fixed 100 kPa — a firmware change not worth making for the key-on reading.

External Link CAN Lambda → ECU (shares CAN1 with the cluster)

The wideband is a Link CAN Lambda module on CAN1 — the same bus the cluster is on. Use its factory defaults (device identifier 0, 1 Mbit/s) — a single module needs no reconfiguration. The ECU receives it into Lambda 1, then forwards Lambda 1 to the cluster on 0x3EA above. See docs/datasheets/LinkCANLambda-manual.pdf.

Configure the XtremeX to receive it (PCLink)

  1. ECU Controls → CAN Setup. In the Mode tab select the CAN module wired to the Lambda (CAN1); set CAN Configuration to User Defined, Bit Rate 1 Mbit/s.
  2. In the Data box, pick a free channel, set Mode = Link CAN-Lambda, CAN ID = 950, format Normal. (This is the receive setup — it fills the Lambda 1 parameter.)
  3. CAN Devices tab → Find Devices → confirm the module appears assigned to Lambda 1.

CAN ID = 950 + device identifier (device 0 → 950/0x3B6). Reconfig commands go on 958 + device id.

No conflict. The module shares CAN1 with the ECU and the cluster (one bus), so "no conflict" here means no two nodes use the same CAN ID — which is what would corrupt arbitration on a shared bus. The module's IDs 0x3B6/0x3BE (950/958) are distinct from the cluster block 0x3E8–0x3EE (1000–1006) and the cluster's own TX 0x3EC/0x3ED, and every node runs 1 Mbit/s — so nothing collides.

Cluster → ECU — the ECU must RECEIVE these

Sent by the two dash rotary encoders (EC11-style, each with an integral push button) — turn the encoder to choose an index, press to transmit it. They are not plain buttons.

Apply & validate (PCLink)

  1. Global: CAN → Custom Setup → Custom stream, 1 Mbit/s, Big endian. Transmit streams 0x3E8–0x3EB and 0x3EE.
  2. Enter each channel exactly as the ENCODE columns above (byte, size, multiplier, offset). Only assign the channels listed — extra channels waste bus bandwidth.
  3. Set up the CAN1 Link CAN Lambda receive (section above) so Lambda 1 is populated before it's forwarded on 0x3EA.
  4. Set up the ECU to receive 0x3EC (boost-map index) and 0x3ED (TC index) — the cluster's boost-map and TC rotary encoders transmit these to switch the ECU's boost map and traction level.
  5. CAN → Monitor: confirm 0x3E8–0x3EB and 0x3EE appear at their cycle times; cross-check values against the runtime page (should match within rounding).
  6. Power the dashboard: gauges track within ~2 s; an engine-protection flag raises the right-cluster warning overlay.
